# Личная очередь распознавания через Supabase и Codex CLI

Эта часть связывает телефон с локальным обработчиком на компьютере. Сайт и вход доступны через интернет, а Codex запускается только на компьютере владельца. При выключенном компьютере задания остаются в очереди. Нужны отдельный проект Supabase и его настройка; миграция не применена автоматически.

## 1. Создать и настроить проект

1. Создайте проект на бесплатном тарифе Supabase. Выберите доступный близкий регион, задайте отдельный надёжный пароль базы и сохраните его у себя. Пароль базы приложению и обработчику не нужен.
2. В SQL Editor выполните файл `supabase/migrations/202610280001_private_recognition_queue.sql` целиком. Он создаёт новую таблицу, функции и закрытый bucket `vmeste-documents`. Если такие объекты уже существуют, миграция намеренно останавливается, чтобы не перезаписать существующие данные или правила.
3. В Authentication включите Email/password и оставьте подтверждение email. Укажите Site URL `https://zaladdin.github.io/Vmeste/`, а для локальной проверки добавьте `http://127.0.0.1:3000/` в разрешённые redirect URL. Создайте свой аккаунт в приложении и подтвердите email.
4. Для личного проекта после создания аккаунта можно отключить регистрацию новых пользователей в настройках Auth. Это не отключает вход существующего владельца. Не выключайте RLS и не делайте bucket публичным.
5. В настройках API проекта найдите Project URL и **Publishable key**. В старых проектах эквивалентная публичная пара называется URL + anon key. **Secret/service_role key, пароль базы и авторизацию Codex ни в приложение, ни в GitHub, ни в чат передавать не нужно.**

Публичные настройки сборки:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
```

Для локального запуска их задают в игнорируемом `.env.local`, для сайта — в окружении его сборки. После изменения нужна новая сборка/публикация. Публичный ключ сам по себе не даёт доступ к личным данным: запросы дополнительно требуют пользовательскую сессию и проходят RLS.

## 2. Запустить обработчик на компьютере

Используется тот же проект Supabase и тот же личный аккаунт, что на телефоне. Отдельный `service_role` не нужен.

```powershell
npm ci
npm run build
npm run start
```

В другом терминале:

```powershell
npm run worker:login
npm run worker:once
# После проверки — постоянное ожидание новых заданий:
npm run worker
```

`worker:login` запрашивает email и пароль интерактивно. На Windows сессия хранится зашифрованной через DPAPI CurrentUser в `%LOCALAPPDATA%/Vmeste/<хэш-проекта>/worker-session.dpapi`; на Linux/macOS — в пользовательском `~/.local/state/vmeste/<хэш-проекта>/worker-session.json` с правами каталога 0700/файла 0600. Пароль не нужно записывать в исходники или присылать в чат. Сессия Supabase и существующий вход Codex остаются на компьютере. `codex login status` должен подтверждать вход через ChatGPT.

Один обработчик запускается для одного локального проекта. Блокировка удерживается локальным TCP-сокетом на `127.0.0.1`, без HTTP/API и доступа из сети. Порт определяется по каноническому пути проекта (20000–39999). После завершения процесса, включая аварийное, операционная система освобождает сокет. `.local/cloud-worker.lock` новой версии содержит только служебные сведения (версия, PID, порт), не является самой блокировкой и остаётся после остановки. Удалять его для штатного перезапуска не нужно. Занятый порт означает работающий обработчик **или другое локальное приложение**, а не подтверждённую готовность Codex; при конфликте обработчик останавливается, а не выбирает другой порт.

Для проверки блокировки без входа, чтения очереди и запуска модели:

```powershell
npm run worker:status
```

При первом переходе со старой версии пустой или повреждённый файл блокировки намеренно не игнорируется. Сначала остановите **все обработчики старой версии этого проекта**, затем выполните:

```powershell
npm run worker -- --recover-lock
```

Этот флаг разрешает переход старого файла на новый формат только после получения свободного сокета. Он не обходит занятую блокировку, не сбрасывает дневной лимит и не перезапускает задания `processing`. Дальнейшие запуски: обычный `npm run worker`. Команда `worker:status` проверяет только блокировку в момент вызова; она не подтверждает вход, доступность сервера или здоровье модели и пока не показывает состояние на телефоне.

Обработчик использует только loopback-сервер `http://127.0.0.1:3000`; при необходимости его адрес задаётся `VMESTE_LOCAL_SERVER_URL` и должен оставаться loopback. Не открывайте локальный сервер в интернет и не пробрасывайте к нему порты роутера. С телефона задания приходят через Supabase, а не через доступ к терминалу компьютера.

Дневной лимит, проверка файла, текстовый путь PDF с переходом к изображениям и учёт реальных токенов остаются в существующем локальном API. Две попытки модели занимают две единицы дневного лимита. Supabase и размещение сайта не делают распознавание бесплатным: Codex расходует лимиты/кредиты аккаунта.

## 3. Контракт очереди

Все RPC возвращают массив строк `recognition_jobs`: enqueue/complete/fail — одну строку, claim — ноль или одну. Запросы выполняются с JWT текущего пользователя; без входа недоступны.

| Операция                   | RPC и параметры                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Загрузка оригинала         | bucket `vmeste-documents`, путь `USER_UUID/JOB_UUID/document`, `upsert:false`                                                                                 |
| Создание/idempotent повтор | `enqueue_recognition_job(p_id uuid, p_attempt_id uuid, p_document_id uuid, p_trip_id text, p_fingerprint text, p_name text, p_mime_type text, p_size bigint)` |
| Взять одно своё задание    | `claim_recognition_job()`                                                                                                                                     |
| Сохранить результат        | `complete_recognition_job(p_id uuid, p_worker_token uuid, p_result jsonb)`                                                                                    |
| Завершить с ошибкой        | `fail_recognition_job(p_id uuid, p_worker_token uuid, p_error text)`                                                                                          |

`p_error` — только код `recognition_failed`, `daily_limit`, `invalid_document` или `worker_unavailable`. База сохраняет соответствующее фиксированное русское сообщение, а не исходный текст исключения, токены или вывод CLI.

`id` и `attempt_id` генерируются клиентом; повтор сетевого запроса использует те же значения и возвращает ту же строку. Для явной новой попытки нужны новые job/attempt UUID. `trip_id` — локальный идентификатор до 100 символов, включая `istanbul-example`; это не ключ доступа. `document_id` — UUID локального загруженного документа. Файл должен существовать до enqueue; база сверяет его MIME и размер с метаданными Storage. Допустимы PDF/JPEG/PNG/WebP размером от 1 байта до 20 МиБ.

Переходы состояний: `queued → processing → completed` или `queued → processing → failed`. Claim использует `FOR UPDATE SKIP LOCKED`, поэтому два обработчика не берут одно задание. Завершение проверяет владельца, статус и случайный `worker_token`. Прямые insert/update/delete таблицы закрыты, собственные строки можно читать. Browser и обработчик имеют одну личную Auth-идентичность: worker-token защищает от случайных устаревших завершений, но не является отдельной ролью или границей доверия внутри аккаунта владельца.

**Автоматического повторного захвата `processing` нет.** Если компьютер завершился после вызова Codex, нельзя достоверно определить, были ли уже потрачены токены. Сначала проверьте/остановите старый обработчик, затем явно повторите задание. Автоматический повтор мог бы привести к повторной оплате.

В первой версии восстановление зависшего `processing` выполняет владелец проекта через SQL Editor, после остановки старого обработчика. Подставьте ID конкретного задания и пользователя из Table Editor; не изменяйте остальные строки:

```sql
update public.recognition_jobs
set status = 'failed',
    error = 'Локальный обработчик недоступен. Проверьте его на компьютере.',
    completed_at = now()
where id = 'JOB_UUID'::uuid
  and user_id = 'OWNER_UUID'::uuid
  and status = 'processing'
returning id, status;
```

После обновления раздела документов появится обычная кнопка повторного распознавания. Новая попытка может повторно расходовать кредиты, если предыдущая уже успела вызвать модель. Автоматического восстановления и кнопки отмены ожидающего задания пока нет; ожидающие документы не удаляются локально до завершения.

Сейчас это очередь распознавания и приватные оригиналы, а не полная облачная синхронизация всех поездок или приглашения участникам. Удаление локального файла из IndexedDB само по себе не означает удаления оригинала из Storage. Пока управление сроком хранения не реализовано в интерфейсе, удаляйте ненужные оригиналы через Dashboard Storage/API. Не удаляйте строки `storage.objects` вручную SQL: это метаданные, а сам файл может остаться в хранилище.

## 4. Проверки перед реальным использованием

Миграция прошла статическое ревью специалистом по PostgreSQL. Пользователь выполнил её в SQL Editor и получил `Success. No rows returned`. Дополнительно API подтвердил существование `recognition_jobs` и отказ анонимному запросу (HTTP 401, PostgreSQL 42501). Это пока не проверка всех функций, RLS или Storage с двумя аккаунтами: автоматический Supabase-коннектор возвращает `Unknown tool`. Ниже перечислены оставшиеся проверки на синтетическом билете без персональных данных.

Проверка структуры в SQL Editor:

```sql
select relrowsecurity from pg_class where oid = 'public.recognition_jobs'::regclass;
-- true
select has_table_privilege('authenticated', 'public.recognition_jobs', 'SELECT') as can_read,
       has_table_privilege('authenticated', 'public.recognition_jobs', 'INSERT') as can_insert,
       has_table_privilege('authenticated', 'public.recognition_jobs', 'UPDATE') as can_update,
       has_table_privilege('authenticated', 'public.recognition_jobs', 'DELETE') as can_delete;
-- true, false, false, false
select has_table_privilege('anon', 'public.recognition_jobs', 'SELECT');
-- false
select has_function_privilege('anon', 'public.claim_recognition_job()', 'EXECUTE') as anon_claim,
       has_function_privilege('authenticated', 'public.claim_recognition_job()', 'EXECUTE') as owner_claim;
-- false, true
select proname, prosecdef, proconfig from pg_proc
where oid in ('public.claim_recognition_job()'::regprocedure,
              'public.complete_recognition_job(uuid,uuid,jsonb)'::regprocedure,
              'public.fail_recognition_job(uuid,uuid,text)'::regprocedure);
-- prosecdef=true; proconfig contains search_path=""
select id, public, file_size_limit, allowed_mime_types from storage.buckets
where id = 'vmeste-documents';
-- public=false, limit=20971520, exactly the four allowed MIME types
```

Проверки API с двумя отдельными тестовыми пользователями A и B:

1. Без сессии таблица, claim и private download недоступны.
2. A загружает synthetic PDF в свой фиксированный путь и создаёт задание; повтор с тем же attempt UUID возвращает тот же job ID. Enqueue до загрузки, с чужим путём, неверным MIME/размером и некорректным форматом fingerprint отклоняется. Совпадение fingerprint с байтами проверяет обработчик после скачивания, до вызова модели.
3. B не видит строку A, не скачивает/удаляет его файл и не может завершить/испортить его задание даже зная ID и worker-token. Проверьте также отсутствие более широких разрешающих policies от других экспериментов в проекте: policies одного типа объединяются через OR.
4. Прямые изменения таблицы от A и B запрещены. Загрузка с `upsert:true` не может заменить существующий файл — UPDATE policy отсутствует.
5. Два параллельных claim от A получают разные задания либо один пустой ответ. У единственного queued job должен быть только один получатель.
6. Неверный worker-token, повтор complete уже завершённого job и завершение чужого job отклоняются. Пустой `events:[]` является корректным результатом, но произвольный JSON, лишние поля, более 50 событий, 20 предупреждений или результат свыше 256 КиБ — нет.
7. Завершите обработчик после claim: новое выполнение не должно автоматически брать processing job. Повтор должен быть осознанным действием владельца.
8. На тестовом билете проверьте появление обоих сегментов в плане, отсутствие дублей при обновлении страницы, запись фактических токенов и соблюдение локального дневного лимита.

Ни эта инструкция, ни проверка исходников не заменяют эти реальные проверки. До их выполнения не включайте обработку документов других людей.

Справка: [Database functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage schema](https://supabase.com/docs/guides/storage/schema/design).

## Локальная проверка реализации

187 тестов прошли после основной реализации; дополнительный regression проверяет восстановление после потерянного ответа загрузки и отказ при несовпадении байтов. Браузерная проверка с имитацией Supabase прошла на мобильном размере: вход, одна загрузка/создание задания, свободный интерфейс во время ожидания, восстановление того же задания после reload, импорт двух перелётов из валидированного результата, защита от повторной отправки. Это не живой тест Supabase и не вызов Codex. Проверка `worker:once` без личного входа корректно останавливается и просит выполнить `worker:login`.

Реальные Windows DPAPI-тесты используют только синтетические строки: проверены шифрование, повторное чтение, атомарная запись, повреждение хранилища и ошибки сохранения. Проведены PostgreSQL, TypeScript, React, general и security review. Найденные ошибки устаревшего опроса, повторного применения результата и защиты сессии исправлены. `image-size` обновлён до исправленной версии 2.0.4; аудит production-зависимостей не выявил уязвимостей.
