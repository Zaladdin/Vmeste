# Комнаты поездок и аккаунты участников

## Включение в Supabase

1. Откройте SQL Editor проекта `ossnsugnmfmoswjojcpp`.
2. Создайте новый запрос, вставьте весь файл `supabase/migrations/202610280003_trip_rooms.sql` и нажмите **Run**. Ожидается `Success. No rows returned`.
3. Обновите приложение. В разделе **Комнаты поездок** нажмите **Проверить подключение**, если он уже был открыт.

Эта миграция добавляет таблицы и функции комнат. Она не переносит личные поездки, не открывает доступ к исходным PDF и не меняет правила облачного распознавания. Файл `supabase/tests/trip_rooms.sql` предназначен только для отдельной одноразовой тестовой базы: в рабочем Supabase его запускать нельзя.

## Как пользоваться

- **Мой ID** вверху страницы — постоянный UUID аккаунта Supabase, одинаковый на разных устройствах.
- **ID участника** во вкладке **Люди** — идентификатор человека в плане поездки. Он сохраняется при редактировании имени; это отдельная сущность, которая может ещё не иметь аккаунта.
- Организатор выбирает свою поездку и нажимает **Создать комнату этой поездки**. В комнату публикуется снимок плана: события, люди и заметки. Оригиналы файлов, задания распознавания и данные входа не передаются.
- Организатор копирует **Код приглашения** и отправляет друзьям. Код показывается после создания или замены. Сохраните его перед закрытием окна.
- Друг входит в свой аккаунт, открывает **Комнаты поездок**, вставляет код и нажимает **Войти в комнату**. Личная поездка для входа не требуется.
- В комнате организатор выбирает присоединившийся аккаунт напротив нужного человека и нажимает **Сохранить привязку**. Один аккаунт связан не более чем с одним человеком в одной комнате. Привязки по совпадению имён не создаются.
- **ID комнаты** служит для идентификации; вход по одному ID не разрешён. Для входа требуется действующий код приглашения.

## Права и обновления

Участники читают общий план, но не редактируют его и не меняют привязки. Организатор редактирует личный план и явно нажимает **Опубликовать изменения поездки**. Сохранение проверяет номер версии: устаревшая версия не перезаписывает новую. Комната обновляется каждые 15 секунд и при возвращении фокуса в окно. При отказе в доступе или неудачной проверке открытый снимок скрывается. Он не сохраняется в личную IndexedDB.

Организатор может заменить код: старый перестаёт действовать, а уже вошедшие участники остаются. Удаление участника снимает его привязку, закрывает доступ и автоматически меняет код, чтобы удалённый аккаунт не вернулся по старому приглашению. Удаление комнаты сохраняет личную поездку и документы. Личные поездки всех аккаунтов по-прежнему изолированы.

Начальные ограничения: до 20 собственных комнат, 50 комнат на аккаунт и 50 аккаунтов в комнате. В опубликованном плане допускаются до 50 людей, 1000 событий и 1 МиБ JSON.

## Проверки реализации

Миграция проверена на отдельной PostgreSQL 16: анонимный доступ, изоляция постороннего аккаунта, запрет прямых записей, вступление по коду, права организатора, привязки, конфликт версий, отзыв доступа, замена кода и пределы коллекций/комнат. Тестовые заглушки Supabase Auth не заменяют рабочую службу Auth.

Браузерный тест с синтетическими аккаунтами и имитацией RPC проверяет создание, вход второго аккаунта, привязку существующего человека, чтение общего плана, порядок событий с разными часовыми поясами, недействительный старый код, скрытие комнаты после отзыва доступа и закрытый интерфейс при отсутствующей миграции. Проверены мобильный и широкий экраны. Реальный облачный запуск требует выполнения миграции выше.
